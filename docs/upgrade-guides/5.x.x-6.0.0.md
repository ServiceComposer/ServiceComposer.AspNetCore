## EnableCompositionOverControllers() is obsolete

`EnableCompositionOverControllers()` is obsolete, and calling it is a compilation error. Code compiled against 5.x that calls it gets a `NotSupportedException` at startup. The MVC result filter it enabled, which ran composition handlers over all controllers, is removed. The method itself will be removed in version 7.0.0.

Call `WithCompositionOverControllers()` on the controller endpoints instead:

```cs
// Before
builder.Services.AddViewModelComposition(options =>
{
    options.EnableCompositionOverControllers();
});

// After
builder.Services.AddViewModelComposition();

app.MapControllers()
    .WithCompositionOverControllers();
app.MapCompositionHandlers();
```

Differences:

- Composition over controllers is enabled only for the endpoints `WithCompositionOverControllers()` is called on. To keep composing over all controllers, call it on the builder returned by `MapControllers()`.
- Composition handlers run as an endpoint filter, not as an MVC result filter. Endpoint filters added before `WithCompositionOverControllers()` wrap both the controller action and the composition handlers, and an action result set by a composition handler with `SetActionResult` replaces the controller action result. Composition handlers run before the `OnActionExecuted` part of MVC action filters, and don't run if an action filter short-circuits the request. See [composition and endpoint filters](../composition-over-controllers.md#composition-and-endpoint-filters).
- When the controller action returns a model, composition handlers compose into it instead of into a new view model. Handlers writing through `dynamic` (`vm.Foo = ...`) fail at runtime if the model's type doesn't have those members.
- Route matching case sensitivity is set with `WithCompositionOverControllers(useCaseInsensitiveRouteMatching: false)`.

## MapCompositionHandlers() returns CompositionEndpointConventionBuilder

`MapCompositionHandlers()` returns `CompositionEndpointConventionBuilder`, which implements `IEndpointConventionBuilder`, instead of `IEndpointConventionBuilder`, so libraries can add extension methods that apply only to composition endpoints. Code calling it compiles unchanged. Libraries compiled against 5.x that call `MapCompositionHandlers()` must be recompiled against 6.0.0: they fail at runtime with a `MissingMethodException` otherwise.

## View model factories returning null fall through

A view model factory returning `null` now falls through to the next one: an endpoint scoped factory to the global one, and the global one to the default `dynamic` view model. Before, the composition handlers got a `null` view model. `IViewModelFactory.CreateViewModel()` is annotated as returning `object?`. See [view model factory](../view-model-factory.md#resolution-order).

## Responses use the minimal APIs JSON options

When output formatters aren't used, the default, composition responses are serialized with the minimal APIs JSON options, configured with `ConfigureHttpJsonOptions()`, instead of ServiceComposer's own settings. Applications that configure nothing get the same output: camel case. Applications calling `ConfigureHttpJsonOptions()` see their settings, e.g. naming policy and converters, apply to composition responses too, which can change their output.

`DefaultResponseCasing`, when set explicitly, and the `Accept-Casing` header replace only the naming policies. `UseCustomJsonSerializerSettings()` replaces the options entirely, as before. See [response serialization casing](../response-serialization-casing.md#minimal-apis-json-options).

## Declarative model binding errors return 400

If a model declared with the `Bind*` attributes has binding errors, e.g. a value that can't be converted, malformed JSON, or a missing required body, the request gets a `400 Bad Request` with a validation problem details body, and no composition handler or endpoint filter runs. With composition over controllers, the controller action doesn't run either: the handlers' models are now bound before it. Before, the composition handlers ran with the partially bound models. `request.Bind<T>()` throws a `BadHttpRequestException` on binding errors, which composition turns into the same response. `TryBind<T>()` still returns the errors without throwing. To keep the previous behavior for both, set `options.ModelBinding.FailOnBindingErrors` to `false`. See [binding errors](../model-binding.md#binding-errors).

## Authorization attributes on handler classes, and [AllowAnonymous] across handlers

Two authorization fixes change which requests composition routes accept. They're also in [5.3.1](https://github.com/ServiceComposer/ServiceComposer.AspNetCore/releases/tag/5.3.1) and [4.3.3](https://github.com/ServiceComposer/ServiceComposer.AspNetCore/releases/tag/4.3.3), so applications already on those versions have them:

- Attributes on composition handler classes become endpoint metadata, as attributes on their methods do, with the method's winning. Authorization attributes on handler classes, including contract-less ones, used to be ignored, and are now enforced.
- If any handler of a route requires authorization, `[AllowAnonymous]` on another handler of the same route is ignored, and a warning naming the handlers is logged at startup. One handler's `[AllowAnonymous]` used to disable the authorization of all the route's handlers.

Before upgrading from an earlier version, check:

- **Authorization attributes on composition handler classes**, such as `[Authorize]`, `[AllowAnonymous]`, or custom policy attributes. Their routes start enforcing them.
- **Routes mixing handlers marked `[AllowAnonymous]` with handlers requiring authorization.** They start requiring authorization.
- **Routes meant to stay public.** Remove the `[Authorize]` that now applies to them, or move what's public to a route of its own.
- **Clients of the affected routes.** They need to send credentials, otherwise they get a `401` or `403`.

See [authentication and authorization](../authentication-authorization.md), and the security advisories [GHSA-mh5p-7fmw-pw24](https://github.com/ServiceComposer/ServiceComposer.AspNetCore/security/advisories/GHSA-mh5p-7fmw-pw24) and [GHSA-rfp4-mgx6-3c5x](https://github.com/ServiceComposer/ServiceComposer.AspNetCore/security/advisories/GHSA-rfp4-mgx6-3c5x).
